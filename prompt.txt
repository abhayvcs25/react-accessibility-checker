# 5. Six-model parallel assessment architecture

This is one of the most important requirements.

The six models must be capable of working in parallel.

The intended assessment workload is:

- Approximately 10–20 React pages in the future.
- Multiple components within those pages.
- 20 contextual accessibility rules.
- Each model receives relevant component context and the rules it must evaluate.
- Each model returns a small structured assessment, not a long report.

Do not send an entire website blindly to every model.

Create bounded assessment jobs using the extracted context.

The architecture must support distributing component-level assessment jobs across all six models.

Do not assume that one HTTP request per website is sufficient.

The scheduler must support:

- Multiple batches.
- Multiple components per website.
- Rule-specific assessment jobs.
- Six independently configured models.
- Parallel execution.
- Bounded concurrency.
- Provider-specific concurrency controls.
- Provider-specific rate-limit handling.
- Token-budget management.
- Retry policies.
- Partial failures.

Do not use unrestricted `Promise.all()` for hundreds of requests.

Use a bounded worker/batch execution design.

# 6. Critical requirement: persistent batch and request tracking

I do not want repeated accessibility checks.

The system must remember exactly:

- Which project or website was analysed.
- Which project version or content snapshot was analysed.
- Which batch was created.
- Which model received each request.
- Which provider handled the request.
- Which component was being assessed.
- Which accessibility rules were included.
- What context/evidence was sent.
- When the request was sent.
- Whether it completed successfully.
- Whether it failed.
- Whether it was retried.
- What response was received.
- Whether the response passed validation.

Design a persistent request and batch ledger.

Inspect the existing database and persistence architecture before choosing where to store it.

Do not introduce an unnecessary database or duplicate storage system.

The ledger should have appropriate fields, such as:

- project/snapshot identifier
- batch identifier
- assessment job identifier
- provider
- model ID
- component identifier
- rule identifiers
- context hash
- prompt/schema version
- request status
- attempt number
- provider request ID, if available
- creation and completion timestamps
- response reference or stored result
- response validation status
- error classification

Use a deterministic idempotency key based on the relevant project snapshot, model, component, rules, context and prompt/schema version.

Before scheduling a job:

1. Check whether the exact assessment already exists.
2. If a valid completed assessment exists for the same snapshot and configuration, reuse it.
3. If the request is already in progress, do not create a duplicate.
4. If it failed with a retryable error, follow the retry policy.
5. If it failed permanently, preserve the failure status.
6. If the project content or assessment configuration changed, create a new assessment version.

Important distinction:

Deduplication must prevent repeated execution of the same model-component-rule-version assessment.

It must NOT accidentally prevent different models from assessing the same component. Independent model assessments are intentional.

Handle uncertain request outcomes carefully. Do not blindly resend requests when it is unclear whether the provider already processed them.

# 7. Output acceptance and validation

Do not assume all six providers accept the same JSON output configuration.

For EACH model, inspect its official documentation and establish:

- Whether JSON mode is supported.
- Whether JSON Schema constrained output is supported.
- Whether structured output is supported through the exact API endpoint being used.
- What parameter names are required.
- Whether the model has limitations on schema complexity.
- What finish reasons indicate a complete response.
- How incomplete or truncated responses are represented.
- How token usage is returned.
- How errors and rate limits are represented.

Use provider-specific request adapters where required.

Normalize successful responses into one internal assessment contract.

The internal assessment should support:

- `potential_issue`
- `no_issue_detected`
- `insufficient_context`

It should contain only the necessary information:

- Rule ID.
- Component/target ID.
- Status.
- Short explanation.
- Supporting evidence references.
- Confidence, if supported and meaningful.

The output must be small.

Do not request long explanations or unnecessary prose.

Implement server-side validation even when the provider supports JSON Schema.

Validate:

1. JSON syntax.
2. Required fields.
3. Allowed status values.
4. Valid rule IDs.
5. Valid component IDs.
6. Evidence references against the context actually sent.
7. Output size.
8. Completion status.

Never accept truncated JSON as a successful assessment.

Do not treat malformed or incomplete responses as `no_issue_detected`.

Keep incomplete, invalid, unsupported and failed responses distinguishable.

# 8. Model execution and failure isolation

One model failing must not stop the other five.

Examples:

- Groq quota exhausted: Cloudflare models should continue.
- One model returns invalid JSON: other models should continue.
- One provider times out: other provider should continue.
- One model is unavailable: preserve the failure and continue other jobs.

Implement:

- Provider-specific concurrency limits.
- Model-specific rate-limit configuration.
- Retry with backoff only for appropriate transient errors.
- Respect provider `Retry-After` information.
- Avoid retrying permanent errors.
- Maintain a strict ₹0 usage budget.
- No paid fallback.
- No automatic model substitution.
- Track token usage where providers expose it.

The application must be able to report partial results accurately.
